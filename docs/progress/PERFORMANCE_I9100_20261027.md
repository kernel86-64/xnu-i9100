# GT-I9100 slow boot, animation stalls and touch NACK — 2026-10-27

The user reports ~10 minutes to boot, ~one unlock-animation frame per 15 seconds, and no touch response. `deadtouch.jpg` shows successful executable activation, over 40,000 single-sector SD reads, and repeated `I9100 TOUCH poll-error=-2 stage=5`.

For this backend, -2 is an I2C NACK. Polling stage 5 is reached only after successful controller initialization, so this is a runtime transfer failure, rather than the earlier no-input stub. The precise failure point was not recorded by that build.

The source defects below are fixed and host checks pass. The amount of improvement and actual touch/UI operation remain to be checked on the phone.

## Confirmed source defects and corrections

### Microsecond requests could sleep

`IODelay()` calls `delay_for_interval()`. With interrupts and preemption enabled, the ARM `ml_delay_should_spin()` always returned FALSE, so even a 5us GPIO delay could enter `assert_wait_deadline()` / `thread_block()`. This cannot guarantee I2C bit timing and adds scheduling overhead to the SD driver's 10us polls.

For I9100, intervals through 50us now spin against the monotonic clock. Longer delays retain the scheduler path. Short touch transfers additionally disable thread preemption until STOP/recovery completes; hardware interrupts remain enabled. Long startup info-block reads are not guarded against scheduling.

A prefix NACK, which consumes no touch message, is retried once after bus recovery. Partial reads/timeouts are not replayed. No transport error generates a fabricated release.

### SD remained at identification speed

The previous stability build intentionally left the SD host at divider 128, about 200kHz with its nominal parent. At one data bit per clock, reading the tens of MiB shown in the photograph can take minutes before command/software overhead.

Initialization and the three matching raw MBR reads remain at the slow rate. The driver now saves slow MBR and, when present, FAT VBR reference bytes, then tries transfer dividers 2, 4, 8 and 128. It checks CRC/status and compares every byte with those references over repeated reads before accepting a rate. Nominal rates are 12.5MHz, 6.25MHz, 3.125MHz and ~195kHz; actual rates depend on the inherited MPLL rate. These stay in SD default-speed mode and keep the existing 1-bit routing.

Runtime failures stop/recover the card and step down the clock before retrying, including the last known slow rate. No sector is shifted or repaired. Samsung low-frequency RX feedback settings are retained, following [Linux Exynos4 setup](https://github.com/torvalds/linux/blob/v3.0/arch/arm/mach-exynos4/setup-sdhci.c).

### Time conversion overflow and inconsistent units

The old `mach_absolute_time()` path multiplied raw MCT ticks by 1,000,000,000 before dividing by 24,000,000. That 64-bit intermediate overflows at roughly 768.6 seconds of counter time (~12m49s), so a long boot could approach or cross it. Conversion now separates whole seconds and the remainder.

`clock_get_system_nanotime()` also interpreted raw 24MHz ticks as nanoseconds. The I9100 branch now uses the scaled absolute clock, matching its documented 1:1 nanosecond timebase.

The fixed-point timer conversion now computes the full product shifted by 32 without losing high bits to an overflowing intermediate. The host checks compare it against 128-bit arithmetic; ARM production code uses 32/64-bit operations only.

These are established arithmetic/unit bugs. Their exact contribution to the reported animation pauses has not been measured on hardware.

### Full frames used an unoptimized byte loop

`ios7i9100_display_present()` copied 1,536,000 bytes using nested C byte loops in a kernel compiled at `-O0`. It now calls the existing ARM burst `bcopy`: one call for a tightly packed frame, or one per row for padded stride. A data barrier precedes the FIMD trigger. Validation covers the entire pitched source footprint, avoiding out-of-bounds reads when stride exceeds 1920.

This improves the CPU copy path. GPU acceleration is not added, and the generic pmap/cache setup and global compiler optimization level are not changed.

## Host checks and build

- `python3 tools/check_i9100_storage.py`: raw MBR/VBR transfer-clock checks, silent mismatch rejection, CRC fallback during probe and normal I/O, plus the existing SD/FAT/HFS checks.
- `python3 tools/check_i9100_touch.py`: GPIO-edge I2C model, transient/permanent NACK, balanced scheduling guards, bounded stuck-clock failure, protocol and native event serialization.
- `python3 tools/check_i9100_timing.py`: monotonic 24MHz conversion over an hour, the old overflow boundary, full-width fixed-point arithmetic, microdelay threshold, and contiguous/padded framebuffer copies with bounds/guard bytes.

All pass with AddressSanitizer/UndefinedBehaviorSanitizer. XNU and uniLoader build successfully. Final archive/header checks and hashes are recorded in `diagnostics/performance-20261027/` along with the logs.

## Physical checks

Use the new `boot.tar` or `zImage.tar` in the workspace root. Check boot duration, whether the unlock animation advances normally, and a one-finger swipe.

Expected SD diagnostic: `i9100 SD: transfer divider=2 nominal=12500 kHz, raw references verified` (a slower verified divider is valid too). Repeated `retry at slower divider` indicates the selected rate did not remain reliable.

If touch still fails, retain the complete new line:

`I9100 TOUCH poll-error=... phase=... reg=... lines=... power=... recoveries=...`

Phases: 1 START, 2 write slave address, 3 register low byte, 4 register high byte, 5 repeated START, 6 read slave address, 7 data, 8 STOP. `lines` contains GPA1 SDA bit 2 and SCL bit 3 (12 means both high); `power` is the touch enable GPIO. This narrows a persistent NACK without guessing coordinates or changing stored controller tuning.
