# GT-I9100 touch input — 2026-10-27

> **Subsequent device result:** `deadtouch.jpg` shows `poll-error=-2 stage=5` (runtime NACK after initialization) and the user reports severe lag. Microdelay/scheduling and performance fixes are recorded in `PERFORMANCE_I9100_20261027.md`; that document supersedes the initial timing behavior below. Physical retest is pending.

The user reported that the lock screen in `BOOTED.jpg` does not respond to touch. Inspection confirmed that the I9100 board selected the J1 no-input stub in `IOS7LeoHIDTouch.cpp`: startup marked it ready, and polling returned without accessing hardware.

This build adds physical Atmel mXT224/mXT224E input. Host protocol/GPIO/HID checks and the ARM kernel build pass. Physical identification, swipe-to-unlock and further UI interaction still need verification on the phone. The previously booted images and matching symbols remain in `backups/booted-20261027/`.

## Board and protocol sources

Samsung U1/GT-I9100 kernel sources, retained in the CyanogenMod smdk4210 tree:

- [gpio-u1.h](https://github.com/CyanogenMod/android_kernel_samsung_smdk4210/blob/cm-10.1/arch/arm/mach-exynos/include/mach/gpio-u1.h): SDA = GPA1(2), SCL = GPA1(3), power enable = GPL0(3), CHG = GPX0(4).
- [mach-u1.c](https://github.com/CyanogenMod/android_kernel_samsung_smdk4210/blob/cm-10.1/arch/arm/mach-exynos/mach-u1.c): Atmel at I2C3 address `0x4A`, 70ms + 40ms startup delay, saved touchscreen configuration and physical 480x800 output.
- [mxt224_u1.c](https://github.com/CyanogenMod/android_kernel_samsung_smdk4210/blob/cm-10.1/drivers/input/touchscreen/mxt224_u1.c): little-endian 16-bit register addresses, CRC24 info-block check, variable object/report IDs, T5 messages, T9 coordinate packing and orientation-dependent drop bits.
- [gpio-exynos4.c](https://github.com/CyanogenMod/android_kernel_samsung_smdk4210/blob/cm-10.1/drivers/gpio/gpio-exynos4.c): GPIO bank offsets.

Earlier project notes describing this GT-I9100 as an unidentified Melfas/Atmel device were not a sufficient basis for a driver. The new backend follows the standard U1 Atmel wiring and accepts only mXT224/mXT224E family IDs with a valid info-block CRC. Another controller is not silently treated as Atmel.

## Implementation

`i9100_touch_gpio.c` implements bounded open-drain I2C on the dedicated touch GPIOs. It maps GPIO1 (`0x11400000`) and GPIO2 (`0x11000000`), enables the TSP rail, configures CHG as a polled input, recovers the bus and communicates only with `0x4A`. SDA/SCL are released for High and driven only Low; clock stretching and missing ACKs return errors. GPIO updates preserve unrelated pin fields. Cleanup restores owned fields. The hardware I2C controller, PMIC, SD pins and CMU are not accessed by this backend.

`i9100_touch.c` identifies the controller and checks its info-block CRC before accessing configuration objects. T5/T6/T7/T9 addresses, message sizes and finger report IDs come from the actual object table. Existing sensor tuning is retained. Sleep power settings are woken with Samsung's volatile T7 values; T9 sensing/reporting is enabled with readback, followed by calibration and REPORTALL. It performs no reset, NVM backup or firmware update.

Coordinates use the actual T9 ranges and orientation, including 10-bit vs 12-bit message packing, then map to physical portrait pixels `0..479` / `0..799`. The controller already applies its orientation bits, so the software does not apply a second rotation/mirror. Valid T9 release/suppression preserves the last contact coordinates. Actual T6 reset/calibration invalidates active contacts. I2C errors and idle polls do not invent Up events.

The first active finger supplies the existing native iOS digitizer queue. Other fingers are tracked but not delivered as separate contacts: releasing the primary cannot transfer its swipe to another held finger. This initial backend supports single-finger taps and swipes, not multi-finger gestures.

`IOS7LeoHIDTouch.cpp` selects the physical backend only for `EXYNOS4210_I9100`. It retains the service class, plugin properties, user-client methods and queue/backpressure behavior. Polling runs every 20ms and drains a bounded batch; a full queue retains the pending report before reading more hardware. Other boards keep their existing transports. A failed controller probe is logged and reflected as `TouchTransportReady=false`, while HID publication remains available for graphical boot diagnostics.

`IOS7LeoTouchWire.h` retains the 204-byte iOS event ABI. Direct packed-field assignments replace temporary structure copies because those copies produced new unresolved `memcpy.N` symbols with the existing ARM compiler/linker combination. No runtime alias shims were added.

## Verification

Run `python3 tools/check_i9100_touch.py`. AddressSanitizer and UndefinedBehaviorSanitizer checks pass for:

- CRC and object discovery, both family IDs, malformed metadata and failed readback.
- Power wakeup and restrictions on controller writes.
- Coordinate orientation/ranges, edge pixels and 12-bit packing.
- Down, move, release, suppression, calibration, extra-finger ownership and unchanged output after failed reads.
- Bounded message draining and empty queues.
- An I2C slave model driven by GPIO edges: open-drain signaling, exact address/register bytes, repeated START, ACK/NACK, stretched/stuck clock limits and pin restoration.
- Native HID packet size, normalization, sender/timestamp and transition flags.

XNU `RELEASE ARM EXYNOS4210_I9100` and uniLoader build successfully. Packaging checks compare tar members with the current images and validate the Android boot header and embedded kernel payload. Logs and final hashes are retained under `diagnostics/touch-20261027/`.

Host checks do not establish physical timing, controller identity or BackBoard/UI consumption on the device.

## Device checkpoints

Flash the new root `boot.tar` or `zImage.tar`, then try a normal one-finger unlock swipe.

Expected diagnostic sequence (not yet observed on hardware):

1. `I9100 TOUCH init=0 ... id=... T5=... T9=... reports=...` and nonzero `range=...`, `transport=1`.
2. `I9100 TOUCH client ...`, queue mapping and `reader-open` when the userspace consumer attaches.
3. `I9100 TOUCH real-report ... x=... y=... down=1`, then `down=0` when released.
4. `I9100 TOUCH enqueued ...` and advancing `reader-head` show queue delivery; UI response is the final check.

If startup prints a negative `init`, retain that complete line, the `range` line and any `poll-error`. Init stages are 1 = info/CRC, 2 = object validation, 3 = configuration, 4 = ready; polling uses stage 5. Error codes are -1 argument, -2 NACK, -3 clock timeout, -4 bus stuck, -5 protocol/configuration, -6 CRC, -7 not ready.

Pre-change source/documentation files are in `backups/touch-before-20261027/`. `touch-i9100-20261027.patch` records this change; the working boot checkpoint is preserved separately.
